# Rentara workspace foundation and application shell

This repository contains the Rentara application, the implemented RENTARA-FEAT-002 identity/workspace foundation, the RENTARA-FEAT-003 operational/platform shell, the RENTARA-FEAT-004 audit baseline, the RENTARA-FEAT-005 local demo seed, the RENTARA-FEAT-006 property management baseline, the RENTARA-FEAT-007 property structure/unit/assignment baseline, the RENTARA-FEAT-008 amenity/media baseline, the RENTARA-FEAT-009 basic tenant registry, the RENTARA-FEAT-010 contract/occupancy baseline, the RENTARA-FEAT-011 manual Billing Baseline, and the RENTARA-FEAT-012 Maintenance Ticket Workflow Baseline.

## Implemented foundation

- Laravel 12.69.2 (PHP 8.2+), with the Breeze Livewire authentication starter kit, Livewire 3, and Volt routes.
- Tailwind CSS v3/PostCSS and Vite asset tooling.
- Breeze Livewire authentication, email verification, password reset/confirmation, profile, and active-user enforcement.
- User identity status, global platform-only Super Admin, workspace and membership schema, current-workspace resolution and switching, workspace authorization, and member management.
- A config-driven Rentara shell for guarded operational (`/app`) and platform (`/admin`) dashboards, with accessible desktop and mobile navigation.
- Laravel migrations for users, workspace data, audit logs, password-reset tokens, sessions, cache, and jobs.
- Rentara brand SVG source assets at `resources/images/brand/`.
- Append-only audit baseline (`audit_logs` with nullable user/workspace `nullOnDelete` relations and nullable polymorphic auditable): allowlisted events for registration, workspace creation, login success/denied, logout, member lifecycle, and platform-dashboard access; critical writes are transaction-coupled and roll back on audit failure; denied logins are generic (`auth.login_denied`, null relations/values) and IP-bounded at 20/min; request context stores only validated IP plus a `sha256:` UA fingerprint, with secrets/raw UA excluded and Eloquent `user_agent` writes rejected (logger-only query-builder path). There is no audit viewer, listing/API, or audit package.
- Local-only demo seed (`RentaraDemoSeeder`, via `php artisan db:seed` in non-production): active verified `admin@rentara.test` (platform `super_admin`, no workspace membership), `owner@rentara.test` (canonical owner), `manager@rentara.test`, and `staff@rentara.test` in the `Rentara Demo Property` workspace (`rentara-demo-property`, `Asia/Jakarta`, `IDR`). Password defaults to `password` locally and is overridden by `DEMO_PASSWORD`. The seeder is guarded out of production at both seeder levels and is idempotent on rerun. There is no tenant demo account (deferred).
- Property management baseline (`RENTARA-FEAT-006` as extended by `RENTARA-FEAT-007`): workspace-scoped Property CRUD at `/app/properties` with Indonesian views, assignment-aware role matrix (owner bypass, assigned-only manager/staff, staff read-only, `super_admin` denied), soft deletes with owner-only restore (restore conflict returns 422) and no force delete, and server-side `workspace_id`/`created_by` assignment. Property structure hierarchy (buildings/floors/blocks), workspace-level unit types, units, and property assignments are implemented; property audit events remain out of scope.
- Property structure/unit/assignment baseline (`RENTARA-FEAT-007`): buildings/floors/blocks scoped by workspace+property and unique per property (`unique(property_id, name)`); workspace-level `unit_types` (`unique(workspace_id, name)`); units with full handoff columns (`workspace_id`, `property_id`, `building_id`/`floor_id`/`block_id`/`unit_type_id`, `unit_number`, `name`, `area`, `rental_price`, `rental_period`, `capacity`, `status`) plus `UnitStatus` (`available`/`occupied`/`maintenance`) and `RentalPeriod` (`daily`/`monthly`/`yearly`) enums; per-property duplicate rules reject trashed-name/number reuse; sibling FKs must belong to the same property (unit types must belong to the same workspace); `property_assignments` (`unique(property_id, user_id)`) with migration backfill and owner-only management. Scoped indexes back workspace/property lookups. Amenity/private-media behavior is documented under `RENTARA-FEAT-008` below.
- Amenity/media baseline (`RENTARA-FEAT-008`): workspace-scoped soft-deleted amenities can be assigned to units only within the same workspace. Property and unit images are private local-disk files, limited to JPG/JPEG/PNG/WEBP and 10 MB, stored under UUID-based paths and served only through authorized workspace/property streams with `X-Content-Type-Options: nosniff`; there is no public media endpoint, image processing, or cloud storage integration. Owner/manager/staff permissions are assignment-aware for media, while amenity catalog writes are owner/manager-only. Amenity/media writes do not emit audit events.
- Basic tenant registry (`RENTARA-FEAT-009`): private, workspace-scoped tenant records support active/inactive lifecycle and soft delete/restore. Each tenant has at most one current unit, while a unit may have multiple tenants; active tenant count is enforced against unit capacity. Identity and other sensitive tenant fields are encrypted at rest, while registry search is limited to contact fields and unit number. Owner access is workspace-wide; managers and staff require assignment to the tenant's property, with managers able to manage and staff read-only. There is no tenant portal, tenant-facing contract/document view, billing, messaging, or tenant audit functionality.
- Contract and occupancy baseline (`RENTARA-FEAT-010`): private, workspace-scoped rental contracts are shared multi-tenant records linked to a property, unit, and existing tenants. Draft/pending/active/expiring/completed/terminated/cancelled lifecycle operations include activation, renewal, cancellation, termination, check-in/out, and manual deposit settlement. Activation enforces active tenants, capacity, non-overlapping active periods, and tenant/unit consistency; it marks the unit occupied. Ending the final active/expiring contract releases the unit to available and clears tenant current-unit assignments, while historical contract, tenant-pivot, check-in, and check-out records are preserved. Owners have workspace-wide access; assigned managers can manage contract structure and lifecycle, while assigned Staff are read-only for contract structure, lifecycle management, and tenant attachment but may perform approved operational check-in, check-out, and manual deposit receipt/settlement actions. Safe contract audit events are transaction-coupled; there is no billing, payment processing, document storage, portal, or messaging.
- Manual Billing Baseline (`RENTARA-FEAT-011`): manual invoices are workspace- and property-scoped records tied to an active/expiring contract, its unit/property, and one responsible active tenant. Amounts are integer workspace-currency values. Invoices are `unpaid` or `paid`; `overdue` is derived only for unpaid invoices whose due date has passed in the workspace timezone. Owners and assigned managers can create/edit unpaid invoice terms; assigned staff can view and record payment but cannot edit terms. One full manual payment records a timezone-safe calendar paid date and one controlled method (`cash`, `bank_transfer`, or `other`). Financial create/update/payment events are transaction-coupled and audit-safe, with restrictive history and no paid-invoice deletion. This baseline has no gateway, partial payments, payment proof, recurring billing, reminders, PDF, invoice items, penalties, utilities, or tenant portal.
- Current verification evidence: `php artisan test` passes **187 tests and 934 assertions**; `npm run build` completed successfully. `RENTARA-FEAT-011` is reviewer-approved and QA-passed.
- Maintenance Ticket Workflow Baseline (`RENTARA-FEAT-012`): internal, workspace/property-scoped maintenance tickets use the lifecycle `submitted`, `reviewed`, `assigned`, `in_progress`, `waiting`, `resolved`, `closed`, and `rejected`. Status history is immutable and audit writes are safe and transaction-coupled. Owners and assigned managers can review, assign eligible assigned manager/staff users, edit, and transition; staff can submit tickets and edit only their own submitted ticket's priority/title/description, while assigned staff can perform operational transitions. Estimated/actual costs and `charged_to` (`owner` or `tenant`) are metadata only and do not create billing. Ticket photos use private local media security. Only owners can soft-delete/restore terminal tickets, and restore checks active parent and assignee validity. There is no tenant portal, messaging/comments/chat, notifications, vendors/SLA, reporting, billing, or payment behavior.
- Current verification evidence: `php artisan test` passes **209 tests and 1005 assertions**; `npm run build` completed successfully. `RENTARA-FEAT-012` is reviewer-approved and QA-passed.

## Scope and documentation

The shell does not implement a tenant portal, tenant documents, messaging/comments/chat, marketplace, dashboard metrics, notifications, a usable workspace-switching interface, or later platform-review modules. Property, unit, tenant, contract, billing, and maintenance-ticket behavior is private and workspace-scoped. Public media, image processing, and cloud storage are not implemented. Dashboard counts remain placeholders. Invitations, ownership transfer, and co-owners are also not implemented. Maintenance tickets do not provide vendors/SLA, reporting, billing/payment, or ticket comments/chat. There is no tenant demo account or tenant demo data. Audit coverage is limited to the baseline, safe FEAT-010 contract events, FEAT-011 financial events, and FEAT-012 ticket events; there is no audit viewer/listing/API, retention/purge, or audit package. No Spatie Permission package is installed.
